# apt packages for the maritime project (gz-maritime, ehukai, and the
# vehicle model repositories).
#
# Hand-maintained on purpose. The source tree is not in the image, so
#
#     drydock run rosdep install --from-paths src --ignore-src -y
#
# against the mounted workspace is what AUTHORITATIVELY resolves dependencies.
# This list just means you rarely have to wait for it. When rosdep installs
# something here, add it to this file so the next image build has it.
#
# Syntax: one package per line, # comments, ${ROS_DISTRO} is substituted.

# ---- ehukai build dependencies --------------------------------------------
# These are here for ehukai, the spectral wave library, and nothing else —
# which is worth stating, because libimath-dev and libtbb-dev are otherwise
# unexplainable lines in a maritime package list.
#
# ehukai is built from source in the workspace like everything else, so the
# image needs what its CMakeLists looks for but not the library itself.
cmake
build-essential
libeigen3-dev
libtbb-dev
libimath-dev

# ---- ArduPilot firmware build dependencies --------------------------------
# waf and Tools/autotest drive subprocesses through pexpect, so a build fails
# on a missing import rather than a missing package. ArduPilot lists it among
# their apt packages, not their pip ones, which is why it belongs here.
#
# Everything else ArduPilot needs in Python — MAVProxy, pymavlink, dronecan,
# empy==3.3.4 — stays out of this file deliberately. Their prereq script puts
# those in a venv on Ubuntu 24.04 and later, and that separation matters: the
# image carries empy 4.2.1 for ament, and ArduPilot pins 3.3.4.
python3-pexpect
ccache
gawk

# MAVProxy's --map and --console modules need wxPython. Taking it from apt
# rather than pip matters: the pip build compiles wxWidgets and takes an hour
# or more, while ArduPilot's venv is created with --system-site-packages, so
# the apt module is visible from inside it.
python3-wxgtk4.0

# ---- ardupilot_gazebo build dependencies ----------------------------------
# For the ArduPilot SITL plugin, built from source in ~/maritime_ws/thirdparty
# rather than as a colcon package. rapidjson-dev and libopencv-dev are already
# pulled in above by other things; these two are not, and the plugin's
# CMakeLists requires them unconditionally even though only its optional
# camera plugin uses them.
libgstreamer1.0-dev
libgstreamer-plugins-base1.0-dev

# ---- misc -----------------------------------------------------------------
libbluetooth-dev
libcwiid-dev

# check_urdf and friends. A <test_depend> of the *_description packages, so it
# is only needed for `colcon test` — but this image is where those tests run.
# The rosdep key is spelled the same as the apt package, which is a coincidence
# rather than the libtbb-dev mistake repeated: `urdfdom` is a different key and
# resolves to ros-${ROS_DISTRO}-urdfdom, the library rather than the tools.
liburdfdom-tools

# Gamepad checks, for answering "is the pad reaching the container at all?"
# before blaming the teleop stack. jstest (from the `joystick` package) reads
# /dev/input/js*, evtest reads /dev/input/event* — and the event device is the
# one that matters here, because bluerobotics_teleop launches the `joy` node,
# which is SDL2-based. Both are console tools on purpose; jstest-gtk exists but
# would only be another thing needing X.
joystick
evtest
